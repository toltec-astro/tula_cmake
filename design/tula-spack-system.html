Problem and decision

One graph model, one package UX

Previous v3 implementation

  • Python models duplicated dependency concepts.
  • Conan, CPM, and system modes required custom dispatch.
  • Owned project dependencies formed a second graph.
  • Bootstrap hid the underlying tools.

Current decision

  • Spack variants describe package choices.
  • Spack recipes own sources, patches, and dependency edges.
  • Environments own compiler/profile policy.
  • Users run native Spack commands.
Boundary: TulaCMake does not decide where dependencies come from and does not manufacture dependency targets.

Public API · target scope

Defaults and diagnostics are explicit

tula_cmake_target_defaults(
  TARGET my_library
  CXX_STANDARD 23
  WARNINGS
)

# Interface targets propagate C++ level only.
# Warning flags stay on compiled targets and
# never leak into installed consumers.
tula_cmake_inspect_target(
  TARGET yaml-cpp::yaml-cpp
  LEVEL DEBUG
  PROPERTIES
    TYPE
    IMPORTED
    INTERFACE_INCLUDE_DIRECTORIES
    INTERFACE_LINK_LIBRARIES
)
Native diagnostics remain primary: --log-level, --log-context, --debug-find, and verbose builds.

Architecture approval checklist

What this round establishes

Implementation

  • CMake-only TulaCMake package
  • installed consumer fixture
  • native Spack matrix
  • logging bundle and perflibs
  • root-controlled transitive variants

Design invariants

  • Spack owns the graph
  • recipes are decentralized
  • Tula is a peer package
  • native UX remains visible
  • capabilities, not providers, reach C++

Approval of this slice authorizes migration of Tula's real dependency surface using the same recipe, installed-target, and test-matrix pattern.
