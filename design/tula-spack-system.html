01 · responsibility

Each layer has one kind of authority

Spack

  • versions and sources
  • variants and conditional edges
  • compiler and platform
  • concrete DAG and prefixes

TulaCMake

  • target-scoped compiler defaults
  • configured/version headers
  • target inspection and logging
  • relocatable package export

Project CMake

  • source and public targets
  • ordinary find_package
  • component definitions
  • behavior tests
No wrapper CLI, Python model, provider manifest, FetchContent dispatch, or second dependency graph is present.

02 · TulaCMake implementation

Package export preserves target-owned usage requirements

install(
  TARGETS ${package_TARGETS}
  EXPORT "${package_EXPORT}"
  ARCHIVE DESTINATION "${CMAKE_INSTALL_LIBDIR}"
  LIBRARY DESTINATION "${CMAKE_INSTALL_LIBDIR}"
  RUNTIME DESTINATION "${CMAKE_INSTALL_BINDIR}"
)

Why this matters

  • The helper no longer injects <prefix>/include.
  • Pure interface adapters may install no headers of their own.
  • Header-owning targets declare explicit build/install interfaces.
  • An installed consumer caught the previous nonexistent-path error.

Deployment-owned

Accepted source revisions, profile selection, platform externals, required release locks, fixture contracts, and uv/Spack activation. Each location keeps spack/<profile>/{spack.yaml,spack.lock,.spack-env/view} together; store and cache are user-shared by default or location-scoped by policy.

Project-owned

Source, CMake targets, package recipes, variants, patches, behavior tests, and local-development package paths remain in each project repository.

tolteca_deploy generates native Spack configuration but keeps spack -e visible. Buildcache publication is deferred and is not required for source-release reproducibility.
